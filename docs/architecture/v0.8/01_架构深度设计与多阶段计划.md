# Procet Studio：业务架构深度设计与多阶段完善开发计划

**版本：V0.8 评审稿｜日期：2026-10-16｜范围：Procet-* 新架构**

本文件结合架构冻结工作台 V0.5、业务数据流 V0.7 与本轮 GitHub 定点源代码审查。11 个二级能力域沿用既有共识；88 个三级能力是原始候选清单，17 个业务数据包是评审基线。本文件新增的接口、责任归属细化和工作包均为建议，不代表已经批准、实现、测试或发布。

本轮未修改仓库，未合并 PR，未启动付费 CI，未运行各仓全量构建、覆盖率或 Windows EXE 验收。文件内 E 编号对应《02_代码证据与差距台账.md》，R 编号对应该文件末尾的官方资料。报告不将 README 的历史测试数量当作当前产品能力证明。

## 1. 结论：以业务能力组织代码，以工程数据组织流程，以可验收切片组织团队

当前最重要的工作不是继续增加仓库，而是使以下六条关系可追踪：

> 业务场景 → 能力职责 → 权威数据 → 应用用例与端口 → 代码实现 → 验收与发布单元。

同一个能力可以由多个包协作实现，同一仓库也可以包含多个有明确边界的能力。团队开发不能仅靠“各自维护一个仓库”实现隔离；它需要确定谁可以改变数据、谁可以依赖接口、如何一起升级、在哪里证明结果可用。

本次代码审查需要修正上一轮的三项过时判断：Host 已经具备统一 Dispatcher、Job、Journal、幂等与策略门，不需要另建一套运行时；Resources 已经使用 exact revision 快照，不应继续把 ID-only/latest 问题描述为当前唯一实现；Knowledge 已复用 Agent 仓的轻量 LLM 客户端，不需要再做一次相同抽取。[E08、E09、E12]

与此同时，现有代码仍有重要的业务架构缺口：GUI 的 CAM 集成依赖旁路工作目录；特征候选入口与已批准 Setup 强耦合；GUI 阶段状态仍为全局单值；仓库最新求解能力没有自动进入桌面锁定的产品组合；CAD/PMI、资源副本与 CAM 公共面尚未完全收敛。[E02、E03、E05、E06、E07、E15、E18]

## 2. 审查基线必须分三层

| 观察面 | 本轮锁定的证据 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| 桌面集成基线 | GUI develop `4e8eec12…` 的 integration-lock.json 与桌面 Cargo.toml | 当前文件声明消费哪些版本 | 不证明本机 EXE 与该组合完全一致 |
| 领域研发基线 | CAM develop `fcec1c86…`；Solver develop `61a61773…` | 对应提交的源码情况 | 不意味着已被 GUI 消费 |
| 未合并开发线 | GUI #60 `c3059a4d…`、#62 `d4b9ff9f…`；Solver #115 `6187462b…` | 某些新代码与任务仍在分支推进 | PR 描述、旧 SHA PASS 不证明该 HEAD 已验收 |

GUI integration-lock 中 Solver adapter/contracts 固定在 `b7e8bfc5…`，并不是本轮 Solver develop 或 #115 的 HEAD。保留已知稳定版本可能是有意的发布决策，不属于自动应当升级的错误。但产品能力目录必须明确展示“已消费能力”和“研发分支能力”的区别。[E03、E04、E18]

桌面 `apps/desktop/src-tauri` 是独立 Rust workspace。根工作区的 `cargo test --workspace` 不覆盖完整桌面构建。团队验收必须同时覆盖两个构建根，以及其实际使用的原生依赖和 Worker 二进制。[E01、E02]

## 3. 多层业务功能与技术分层分别建模

### 3.1 保留原 L1/L2，细化 L3，新增 L4 实现映射

| 层次 | 含义 | 本轮约束 |
|---|---|---|
| L1 | Procet Studio 完整工程应用 | 不因拆仓而拆成互不相通的产品 |
| L2 | 原有 11 个能力域 | 编号和名称保持，代表职责目录而非点击顺序 |
| L3 | 88 个原始候选业务能力及后续修订 | 按真实用例拆分、合并和增补；不能为了整齐强制每域永远 8 项 |
| L4 | 用例服务、领域对象、算法、端口、适配器、包与测试 | 每一项有唯一权责、输入输出、异常语义、来源和验证入口 |

V0.7 已提出 NC 执行适配 D13、轴运动时序 D14。因此，08/09 的三级清单需要显式修订，而不能只在旧标题下面笼统标记“仿真已实现”。附带 88 项映射保留原名称；增补建议单列，避免把新提案伪装成既有冻结结论。

技术分层另行表达为：

```text
GUI / CLI / Agent 客户端
        ↓ 同一能力调用入口
应用用例与业务流程编排
        ↓ 端口、命令、回执
领域服务与领域规则
        ↓ 算法端口 / 持久化端口 / 资源引用
算法实现、原生几何 Worker、数据库、文件与系统适配器
```

共享身份、单位、坐标帧与协议是横向基础，不是让所有业务依赖一个巨型 common 包。ISO/IEC/IEEE 42010:2022 约束架构描述及其视点表达，不规定 Procet 必须采用某个框架；本方案建议分别维护业务、数据、运行时、开发、部署、验收六个视图。[R01]

### 3.2 11 个能力域映射到现有仓库

| L2 | 业务权威 | 建议代码落点 | 必须隔离的责任 |
|---|---|---|---|
| 01 工程工作台与工程管理 | 工程身份、会话、用例组织、受控交接 | procet-gui 的 Project/Host crates 与桌面壳 | 不内置制造算法；Host 不接管各域私有表 |
| 02 制造资源 | 可复用资源定义、修订、能力、安装接口 | procet-resources | 不决定某个工件怎样装夹，不负责运行时 IK |
| 03 CAD / PMI 与制造特征 | 设计语义、拓扑身份、特征与证据 | 现有 CAD/PMI 边界包，procet-2d、procet-docs 协同 | 代码暂在 CAM 不等于业务权属变成 CAM；识别算法可来自 Solver |
| 04 装夹与坐标系 | 工艺 Setup、执行绑定、空间实例关系 | procet-cam 内部 setup 子域 | 不拥有资源主数据，不重复实现变换数学 |
| 05 工艺规划 | 工序、工程决策、采纳、冻结、计划版本 | procet-cam 内部 planning 子域 | 不把候选直接当批准计划 |
| 06 工艺与几何求解 | 搜索、材料状态、局部几何、计算证据 | procet-solver | 不写批准计划，不签发 NC 发布资格 |
| 07 CAM 刀路 | 工序到中立轨迹 | procet-cam 内部 toolpath 子域及受控算法适配 | 不把 CL 等同机床关节轨迹 |
| 08 NC 与后处理 | 后处理、NC 修订、控制器执行语义 | procet-cam 内 post 与 nc-execution 子域 | 生成与解释分开；不得绕过程序字节重新使用旧 CL 冒充验证 |
| 09 机床运动与工程验证 | 运动展开、限位、干涉、分级验证证据 | procet-cam 内 motion 与 verification 子域 | 不由 Babylon 判断工程可执行性 |
| 10 程序发布与现场协同 | 受控发布包、交付、现场反馈 | procet-cam 内 release 子域与外部适配器 | 发布不原地修改上游；反馈须走工程变更 |
| 11 AI 智能体与工艺知识 | 建议、工具计划、检索、知识来源 | procet-agent、procet-knowledge | 不是第二套计划数据库，也不是特权写入通道 |

这是一份建议的逻辑映射，不表示要立即创建所有命名的 crate。优先在原仓内建立边界，再根据独立构建、原生依赖隔离和团队负责人决定物理拆包。现阶段不新增顶层仓库。

## 4. 从业务流程反推最小输入，而不是从页面顺序推门禁

### 4.1 A：工艺探索

A 可从设计目标直接开始；人工计划是可选输入，不是进入 Solver 的硬前置。

```text
设计基线 D01 + 可用特征 D02 + 当前求解所需材料/约束
          ↓
求解候选 D06 ↔ 人工决策 D05
          ↓
局部材料状态 D07 + 采纳/冻结 D08
          ↓ 可在可继承的任一状态交给 B
工程化补全
```

“可直接求解”不等于“完全不需要输入”。纯设计特征识别需要可信模型与拓扑；涉及去料状态的求解需要毛坯与相应约束；涉及特定机床可达性的求解才需要具体执行配置。每个能力返回结构化最低输入要求及缺失原因，不能用一个 Setup Approved 标志统管所有探索。

本轮在 `feature_candidates.rs::run_candidates` 确认了要求非空 setupId、同 Job、Approved 状态的生产式入口。该实现并不能证明独立 Solver 没有直接求解能力；它说明不应把这个入口同时用作所有 A 模式探索入口。[E06]

建议保留既有接口的生产语义，新增清晰分离的用例：设计/制造特征探索、带工艺上下文的特征解释、将候选绑定并采纳到生产工序。不要直接删除原审批校验来迁就 UI。

### 4.2 B：工程生产

B 可以承接 A，也可以直接创建工程。它不要求重新进入“特征分析页面”来获得已经存在的特征数据。

```text
设计与制造要求
    ↓
工艺 Setup D04 + 工艺决策/冻结 D05、D08
    ↓ 生成所需条件具备
中立 CL D09
    ↓ 绑定具体机床、控制器、工件偏置、刀具安装 D10
CL 预验证 D11（单独记账）
    ↓
NC D12 → 执行语义 D13 → 轴运动 D14 → 程序验证 D15
    ↓ 验证、授权与精确版本闭合
发布 D16 → 现场反馈 D17 → 新的工程变更
```

工艺 Setup 和机床执行绑定分开。机床可提前选定以约束规划，也可在只需要中立工艺信息的阶段之后绑定。迟绑定并不保证所有 CL 都可复用：若某刀路算法确实消费了机床特性，相关指纹必须记录在依赖中。

### 4.3 A/B 接管是受控用例，不是复制数据库

A→B 接管的输入是一个可继承工程修订及其对象引用集合。应用层校验来源、选定候选、局部冻结与资产可用性，提交接管记录及 B 待补任务；不复制另一份“工程真相”，不自动取得生产资格。

B→A 回流应指定受影响对象和约束。冻结冲突只能显式拒绝、由有权人员解冻，或创建保留原决策的探索分支。新的候选不能静默替换已冻结工序；未受影响的工序、CL 和历史证据保持可追踪。

业务过程允许循环，版本化产物来源应保持有向无环。比如 D17 的现场意见影响的是新 D05 修订，不是将原发布包的祖先原地改写。

### 4.4 最低要求和生产资格分开

| 用例 | 最低输入示例 | 不应当额外强制 |
|---|---|---|
| 设计特征探索 | CAD/PMI/拓扑及算法所需信息 | 已批准机床 Setup、NC 仿真 |
| 制造材料状态求解 | 目标、毛坯、保护/余量、适用约束 | 人工 Plan、已打开某个 GUI 页面 |
| 中立刀路草案生成 | 工序意图、加工域、工艺 Setup、刀具/策略所需参数 | NC 最终验证 |
| 机床预验证 | CL 与 exact 机床执行配置 | NC 已发布 |
| NC 生成/执行解释 | 生成或解释各自真实必要的输入与适用策略 | 不相关页面访问历史 |
| 受控上机发布 | 精确 NC、执行配置、要求的验证证据、授权 | 不能由“播放完成”替代 |

对于现有要求已提交 Plan 或特定资格的生产接口，保持兼容语义；探索生成需求通过单独草案能力承接。避免全局放宽导致批准与未批准成果混淆。

## 5. 17 个数据包变成工程数据资产目录

V0.7 的 D01—D17 继续保留。这是业务资产种类，不是强制新建 17 张表、17 个服务或 17 个大型通用结构。其原始定义、所有者、上下游已单独导出到 business-assets.json。[历史基线 H02]

每类资产应明确四件事：谁可以写、什么是稳定身份、基于哪些输入得到、变化后谁失效。建议公共引用描述覆盖：

- 对象与修订身份、内容指纹、schema 版本、权属域；
- 依赖对象的 exact 引用及依赖用途；
- 适用时的单位、坐标帧和几何来源；
- Producer 与算法/配置版本、结果能力范围、诊断及证据引用。

以上是待评审语义，不是已经发布的 Rust/TypeScript 字段规范。领域 C1 DTO 仍由领域负责人维护；C0 提供中立运输与公共身份。历史文档 C01—C10 的概念编号不得与当前代码的 C0/C1 分层混为一谈。[E10]

### 5.1 两类身份不能混用

内容 hash 表示冻结字节与输入绑定，不等于几何准确、算法正确或工程安全。跨 OCCT 版本的几何等价也不能仅靠字节 hash 判定。B-Rep 等价、容差和来源映射需要相应的几何核验。

Solver 内部用数组下标表示当前 Run 的候选顺序可以成立；跨工程采纳时应绑定稳定 OperationId/FeatureRef 及其输入序列映射，不能把 `usize` 跨重排直接当业务身份。[E19]

### 5.2 数据变更影响矩阵

| 修改 | 直接处理 | 不应无条件失效 |
|---|---|---|
| CAD/PMI 或真实工艺约束变化 | 按用途追踪特征、计划、求解、CL、NC、验证 | 与变更不相关的历史分支 |
| 工序顺序、保护区、阶段余量变化 | 受影响 D06/D07 及其后续 CL 和执行链 | 未受影响且无依赖的工序 |
| 机床/控制器/工作偏置/刀具安装变化 | D10 及消费它的 D11—D16 | 未消费这些参数的设计语义与中立 CL |
| 手工编辑 NC | 新 D12 修订，旧映射相应失效；重新构建 D13—D16 | 上游 CAD、冻结 Plan、未改 CL |
| 仅替换显示代理 | 重建相关渲染资产 | 真实碰撞几何未变时，不默认作废几何验证 |
| 资源退役 | 历史内容保持；新使用/新发布按政策判定 | 不以状态变化篡改历史内容 hash |
| 主题、面板布局、相机 | 只改变显示/交互状态 | 所有制造资产 |

共享依赖图保存节点、引用及版本关系；“哪些字段影响哪些结果”的规则由领域模块贡献，不能集中到 GUI 的超大 switch 中。

### 5.3 事务与快照

现有 Project Runtime 已具备 generation、SQLite Backup、临时文件校验与原子替换。这是应复用的基础，但单文件原子保存并不自动证明多域数据同时一致。[E20]

建议验收或完善以下流程：读取受控基线 → 各域产生 staging 结果/commit receipt → 宿主验证引用闭包与预期 generation → 提交工程可见引用 → 保存 `.pct`。新域资产已完成但工程基线冲突时，可以保留为未采纳结果，不能覆盖当前工程头。

恢复时先检查必需域、schema 与资产，构建待挂载的读取状态，所有必需项满足后再对用户切换可见工程。不能出现“工程打开成功，但部分域仍是旧状态”。跨数据库一致性采用显式提交/恢复协议，不宣称所有库处于同一个 ACID 事务。

Resources 的 exact refs v2 应继续使用。下一步的验收重点是冻结 typed 参数、装配子件、真实几何资产及其 hash 的完整离线闭包，而不是再写一套 revision 查询器。[E09]

## 6. 应用编排与物理任务运行分层

Host 的 Job、Dispatcher、ProcessSupervisor、Journal、策略门、取消与幂等已经存在。新增业务流程编排应复用它，不另立一个同等地位的任务数据库。[E08]

建议将下列状态分开：

| 状态 | 权威位置 | 典型含义 |
|---|---|---|
| 工程业务状态 | 对应领域与工程修订 | 候选、采纳、冻结、批准、失效 |
| 流程状态 | 应用用例/流程实例 | 当前等待哪些输入、哪些节点可继续 |
| 物理任务状态 | Host Job Runtime | queued/running/取消/失败/终态提交 |
| 资产有效性 | 资产引用与领域失效规则 | 当前输入下是否适用、为何过期 |
| 工程资格 | 分级验证与发布策略 | 特定机床/控制器/能力范围内是否允许下一动作 |
| GUI 状态 | WorkContext 与布局/编辑会话 | 用户正在查看、选择或修改什么 |

同一个 Job 完成不等于资产已被 Plan 采纳，也不等于资产仍适用于当前修订。UI Active 不等于后端 Ready；后端安装成功也不等于任意输入均满足能力条件。

运行时建议统一记录 correlationId、工程/文档/Setup 作用域、输入指纹、调用版本、事件序号与结果回执。跨 Worker 传递大 B-Rep/网格时优先使用受控工件引用和有界读取，不通过巨大 JSON 数组反复拷贝全部几何。

Agent 可以组织建议任务图，但每个有副作用的实际用例仍走同一 Host 能力入口。人类 GUI 与 AI 不应拥有两套不同的提交规则。

## 7. 模块化实施：封装先于拆包，拆包先于拆仓

### 7.1 CAM 收口

当前 CAM 既提供 CamService facade，又公开导出 cad/db/llm/pmi/loader 等模块。公开面扩大允许消费者绕过 façade；这与源码注释中“极小公开面”的目标存在张力。[E05]

建议依次推进：记录真实消费者 → 设立允许的公共 API → 用消费者测试保护 → 内部模块降低可见性 → 移除领域副本依赖 → 按独立生命周期拆 crate。不能直接全仓改为私有而不准备兼容迁移。

最终可形成的仓内边界是 setup、planning、toolpath、post、nc-execution、machine-motion、verification、release；CAD/PMI 与通用数学保持独立语义边界。这里是目标职责，不要求一次性创建八个空包。

跨域读取使用查询端口/只读投影，写入使用领域命令与回执。宿主不能为了显示一个字段直连对方 SQL 表；底层表名也不应成为 UI 契约。

### 7.2 Solver 产品化，不做无必要的语言重写

#115 的 G6 源码明确将强类型接收、预算与诊断同工程安全授权分开，`nc_release_authorized` 必须为 false。这条边界正确，应保留。[E19]

Python/OCP 的验证实现可以作为正式受管 Worker 的起点。缺口在于稳定请求/结果封装、环境锁定、资产导出、超时取消、版本协商、能力范围与宿主消费，而不在于所有算法是否立刻写成 Rust。

应把 `tools/geo03` 的实验脚本经明确入口封装，提供产品级 SolveRun/MaterialState 适配；GUI 不直接 import 实验目录或依赖工作目录存在。保持原几何矩阵、独立 Checker 和 Python→Rust 桥接回归，再考虑性能瓶颈对应的迁移。

独立 Checker 可使用同一 OCCT 内核，但不能直接信任生成器提交的“通过”结论；必须独立重建规定的验证事实，保留证据范围与共享假设。

### 7.3 共享基础不是公共杂物箱

公共基础建议分为：身份/协议；坐标与单位纯数学；几何查询端口；运行时机制；UI/Renderer 端口。每类都有明确 Owner。

`procet-contracts` 不放数据库、UI、算法或调度器；几何实现不依赖 Tauri/React/Babylon；渲染变换不写回工程坐标；业务规则不通过复制代码在多个仓库漂移。

Cargo 支持同一 Git 仓内多个 crate，也支持精确 rev 和 path 等不同来源。团队发布应使用可复现来源；本地联调可以有显式覆盖，但不得让覆盖路径成为生产必需条件。[R04]

## 8. NC 与运动链：生成、解释、展开、验证四项职责

CAM 已有真实后处理 facade，保存全文字节、hash、行与工序映射、输入来源和适用性，不应重新描述为“尚无后处理实现”。本轮没有据此确认 D13→D14→D15 已被桌面端完整独立执行与验收。[E17]

| 环节 | 正式输入/输出 | 必须证明 |
|---|---|---|
| Post | D09 + D10 → D12 | 指令与控制器能力匹配，完整字节可复现，来源映射可读 |
| NC Execution | D12 + exact 控制器配置/初态 → D13 | 模态、偏置、补偿、辅助动作和已支持程序结构的语义明确 |
| Machine Motion | D13 + exact 机床/刀具/装夹 → D14 | 正逆解/轴指令展开、分支连续、限制与时间模型可解释 |
| Verification | D12/D13/D14 + 碰撞及约束事实 → D15 | 对指定覆盖范围给出独立结论与不能证明的内容 |

程序显式给出轴地址与 TCP/RTCP/倾斜平面等命令必须分流。不能为所有模式统一套一次 IK，也不能因为三维播放能走完整条曲线就认为控制器解释正确。LinuxCNC 官方资料分别提供独立解释器和坐标/关节运动学接口，可借鉴职责分离，但不是所有商业控制器方言的替代实现。[R02、R03]

后处理在生成显式旋转轴程序时，可以调用统一运动学服务获得生成所需轴解；禁止复制第二套 IK。随后 D14 仍需从最终 NC 的解释结果独立重建，不能拿生成阶段保留的轴数组当作程序验证证据。

D14 的时间字段应注明是模型估计、已建模控制器规划时间，还是来自现场反馈。没有真实动态模型就不能宣称精确机床节拍。D15 需要标明离散/连续检查范围、容差和未建模行为；离散样点没有碰撞不自动证明连续运动全程安全。本轮不把材料扫掠仿真作为必需开发项。

ISO 841 用于机床坐标与运动命名的规范依据；实际轴树、旋转中心、装夹基准、主轴接口、规长及控制器模式还必须绑定具体设备/控制器资料和测试。不能仅凭“B5”名称决定双摆头、双转台或某个 A/C 轴顺序。[R05]

## 9. GUI 改进：把单容器升级为统一业务任务承载协议

### 9.1 四个正交维度

建议区分：A/B 业务模式、Workbench/AI-native 展示模式、当前任务导航、布局偏好。修改主题或切换展示模式，不应改写 Plan/Setup；进入生产模式也不等于所有验证已通过。

本轮在 #62 HEAD 看到 stageStore 仍使用全局 `currentStage`。这不等于当前单活跃文档一定出错，但它不足以单独描述多个文档、多个 Setup 与返回现场。[E15]

建议以 project/document/setup/plan revision 等稳定引用组成 WorkContext，在其下保存导航与编辑会话。不要把所有领域实体复制进一个万能全局 Store。切换 Setup 后，应直接查询该上下文的 Feature/Plan 只读投影，不依赖用户是否重新访问过“特征分析”。

### 9.2 复用已有 Setup 控制器

`useSetupWorkflow` 已有单一草稿、服务端批准指纹、CAS、作用域代次、晚到回执保护以及 coordinate/native/legacy 策略。应将其经验抽成可复用 EditSession 与 TaskContribution 规则，而不是再建第二个保存/批准控制器。[E16]

统一任务协议建议包含：适用上下文、数据读取、可编辑草稿、输入校验、能力需求、主/次命令、3D 选择意图、预览生命周期、关闭/恢复策略。不同领域表单不必同构，但必须遵循相同的草稿与提交纪律。

### 9.3 3D 选择和工程修改分离

资源列表和 3D 候选共享 SelectionIntent/GeometryRef；预览只产生临时渲染资源，确认才重新解析 exact revision 并调用领域命令。资源网格、加工特征、坐标柄的显示 ID 不成为工程实体 ID。

保留一个 Babylon Engine/Scene/Canvas。工程与资源虚拟桌面采用受控 Session/根节点切换；Overlay 按作用域租约创建和释放。性能测试观察切换后的 GPU/内存是否趋于稳定，并记录参考硬件、模型规模和结果，不捏造未经测量的帧率目标。

### 9.4 显示可行动的工程状态

任务面板应解释“缺哪个输入、哪个版本已失效、去哪里补齐”，而不是仅显示一个灰按钮。建议直接提供“定位缺失坐标”“打开未解析资源”“比较失效工序”等修复入口。

NC 文本、执行语义、轴运动和验证事件使用同一来源映射联动；手动改 NC 后显示新版本及待重新解释状态。Solver 曲线来自真实诊断数据，明确不是安全概率。

玻璃、浅/深主题、悬浮 Ribbon、状态栏与安全区仍沿用既定设计。状态变化应以可读文字、焦点与可访问语义表达，不能只依赖流光。W3C 状态消息指导可用于交互验收，不意味着已取得桌面无障碍认证。[R06]

## 10. 团队开发机制，从第一阶段启用

团队开发并不等于此刻就要开发多人在线共同编辑。先确保多名开发者/Agent 能在独立环境中按契约协作，再根据真实产品需求决定共享服务器和在线协同。

建议设定六类责任角色，而不是预设六支满编团队：平台与集成、设计/资源/Setup、几何求解、CAM/NC/验证、桌面体验、AI/知识/文档。质量验证角色贯穿各域，允许一人兼任，但关键发布不以作者自报替代独立验收。

每个 L3 能力绑定：业务 Owner、实现 Owner、消费方 Reviewer、验收负责人、备份维护者。CODEOWNERS 落到真实维护人员前，模板不填虚构账号。

### 10.1 契约变更流程

提出场景与兼容影响 → ADR/RFC → 生产者与至少一个真实消费方共同评审 → 正反例与旧版本 fixture → Producer 合并 → Consumer 更新精确依赖 → 产品组合回归 → 集成锁发布。

不同进程可在经过兼容测试的 wire 版本上协作，不要求所有源码 Git SHA 相同。同一 Rust 进程共享 trait/类型时，必须避免重复来源造成类型身份分裂。[E10、E11、E12]

### 10.2 测试与发布

发布单元是产品组合：仓库 SHA、Cargo/pnpm 锁、Worker 二进制 hash、原生依赖、schema、默认资源包版本、测试证据。单仓测试通过不替代组合测试。

每轮 local verification 必须报告 exact HEAD、环境、命令、PASS/FAIL/BLOCKED/NOT_TESTED、日志 hash、未覆盖范围。新提交后旧 PASS 不继承；PR 正文与实时 HEAD 不一致时，以对应 SHA 的证据为准。

现阶段保持每仓开放 PR 不超过 3、每条主线一个主工作分支；不自动合并、不触发付费 CI。团队扩张后可以重新评审并发限制，但不能用大量长期堆叠分支掩盖尚未集成的工作。

### 10.3 清理旧实现的完成条件

不是“新目录创建成功”就能删除旧代码。需先有真实消费方切换、边界测试、功能/格式兼容验证、回退点和数据迁移方案，再删除生产路径中的旧实现。迁移采用扩展→迁移→收缩，保留可读旧版本，不直接重建用户 SQLite 业务主表。

评估架构质量优先使用跨域越界依赖、重复权威入口、复现成功率、局部失效正确率、契约破坏数量和关键业务回归稳定性。文件行数和测试总数只能作为线索，不能作为能力证书。

## 11. 六阶段完善开发计划

完整 36 个工作包见《04_开发工作包_36项.md》和 work-packages.json。每项包含依赖、Owner 角色、产物、测试、回退与范围排除。均为建议任务，尚未创建远端 Issue/PR。

| 阶段 | 目标 | 关键交付与退出条件 |
|---|---|---|
| B0 现状与业务基线 | 建立共同的真实起点 | 11/88/17 映射、精确产品组合、可重现环境、当前 PR 证据对齐、团队责任与验收规则 |
| F1 契约与模块边界 | 模块可独立开发、受控集成 | C0/C1 边界、坐标/单位、CAM 公共面、双 Setup/探索输入、Solver 受管入口、完整工程快照闭包 |
| W2 业务流程与增量状态 | A/B 协作、多 Setup 不依赖页面顺序 | 接管/回流/局部冻结、依赖失效、并发提交与恢复、完整无界面业务回归 |
| E3 3 轴与 B5 执行链 | 完整且范围可解释的 CL→NC→运动→验证 | D09/D12/D13/D14/D15/D16、真实模型与控制器子集、错误样例必须失败、同一程序版本验证与发布 |

这不是六个互相完全串行的大阶段。B0 的责任和测试规则立刻启用；F1 的关键接口稳定后，W2、E3、U4 可以按工作包依赖并行；每一阶段都必须有真实业务切片，不能先写几个月空接口再第一次联调。

建议关键路径：B0 产品基线 → F1 身份/Frame/双 Setup → E3 真实两机型最小程序闭环 → D15/D16 验收。同时由另一条线推进 W2 的候选/冻结/增量状态，GUI 按同一端口消费，不反向推动领域临时变更。

### 11.1 与 2026-10-24 MVP 的关系

10 月 24 日目标应是明确范围的纵向演示与验收切片，不是 88 个三级候选全部完成，也不是六阶段团队架构全部建设完毕。

限定样例需要做到：安装/打开项目 → 工艺 Setup → 指定机床绑定 → 已支持 CL → 实际 NC 字节 → 已建模解释语义 → 轴时序 → 对声明范围的验证 → 可追溯结果。涉及未知控制器语义、缺失机床/刀具接口、未完成必要验证时，显示 BLOCKED 或未授生产资格，不以演示日期强行放宽。

上述目标能否按期达成，需由当前 exact-HEAD 的本地结果与剩余真实适配量判断。本次静态审查不提供无证据的工期承诺。架构建设与长期扩展按阶段退出条件持续推进。

## 12. 第一轮实施顺序

首先完成 B0 的精确集成基线、现有分支证据和可复现构建。这会立即降低“各仓都有代码、本机却无法一起运行”的风险。

其次落实 F1 的两个关键业务边界：设计/探索特征入口不再复用生产 Approved Setup 门；ProcessSetup 与 MachineExecutionBinding 分开，并建立一组真实坐标与资源快照回归。

然后并行推进 W2 的采纳/冻结/失效切片和 E3 的 D13/D14 接线。GUI 不等待所有算法完成，但只依据正式端口和能力状态显示、选择和发起操作。

整个计划的成功标志不是重命名了多少目录，而是新增成员能够检出已锁定组合、运行一个完整案例、清楚知道改动的权威边界，并证明自己的变更没有破坏其他能力。

## 13. 外部依据的使用范围

本方案将设计、规划、执行、检测区分为相互关联而不互相替代的工程事实，这与 NIST 关于贯通制造数字链的信息需求研究方向相符。[R07] 本文件并不声称已采用该论文全部模型，也不声称符合未经逐项核验的行业标准。标准与官方工程文档用于约束术语、职责和验证思路；具体机床、控制器及软件实现仍须提供自己的来源与证据。
