# 团队开发、变更与验收模板

**V0.8 评审稿｜2026-10-16。模板不是已执行记录；不得把空字段或示例视为验收通过。**

## 1. 模块责任卡

| 字段 | 需要填写的内容 |
|---|---|
| 能力追踪编号 | 关联 L2/L3；沿用原编号或明确新提案 |
| 业务负责人 | 对语义和规则负责的人，不能只填仓库名 |
| 实现负责人/备份 | 真实维护者；允许跨仓有子负责人 |
| 消费方评审者 | 至少一个实际消费接口的维护者 |
| 质量验收者 | 执行或复核测试的人 |
| 唯一写入资产 | 对象种类、修订、状态转移及存储边界 |
| 允许依赖 | 稳定 API、查询端口、协议、资源引用 |
| 不允许依赖 | 私有数据库表、对方 UI、兄弟工作目录、渲染临时 ID |
| 规范与资料 | 标准/控制器/设备手册的版本及适用范围 |
| 回归与故障样例 | 正例、负例、恢复、兼容与性能基准 |
| 发布单元 | crate/Worker/schema/UI contribution 及组合锁引用 |

## 2. 开发任务模板

### 任务身份

任务编号：待填写。关联阶段与能力：待填写。实现仓库与 exact 基线：待填写。

### 要解决的真实业务场景

说明用户从什么工程状态开始，希望得到什么业务结果。不能只写“新增页面”“拆分文件”或“支持五轴”。

### 现有实现及差距

填写真实源路径、函数/类型、读到的行为、对应 SHA。区分已看到代码、只看到设计/PR 描述、已运行测试、尚未验证四种证据。

### 输入、输出与所有权

列出 exact 输入引用、必需条件、条件可选字段、输出资产、写入 Owner、字段变化影响的下游。明确候选、草稿、批准结果和验证证据的差异。

### 实施范围

列出拟改公共接口与内部模块、迁移顺序、真实消费方接线、持久化影响。说明为什么不需要改其他域；确实需要跨域变更则先关联契约变更。

### 不在范围

明确模型/机型/控制器子集、不支持的语义、不会实施的重写、暂不授予的资格。

### 验收

至少包含正常场景、输入错误、作用域/版本过期、重复请求、取消/恢复、旧数据兼容、真实消费方用例。执行命令应由当前仓库实际脚本确认，不写不存在的脚本名称。

### 回退

说明代码回退、组合锁回退、旧 schema 读取、staging 清理和数据恢复。代码 revert 不等于数据库已经回退。

### 交付条件

代码、协议/例子、消费者测试、日志、exact-HEAD 验收、变更说明与未覆盖能力同时齐全；已提交不等于已验收。

## 3. ADR/RFC 模板

标题和编号：待填写。

状态：提议 / 批准 / 被替代 / 撤销。不得自行把提议改为批准。

背景：当前业务用例、代码事实、约束和引发本次决策的问题。

候选：保持现状、渐进适配、模块抽取等真实备选；描述复杂度、迁移成本、可验证性和失败风险。

决定：采用哪种方案及不采用其他方案的理由。

边界：资产 Owner、API/Schema、应用事务、线程/进程、存储和界面生命周期是否改变。

后果：消费者影响、旧数据、离线安装、原生依赖、诊断与恢复。

验证与撤回：对应工作包、正反例、比较基线、回退点。

审批：实际 Owner、消费方 Reviewer 和批准日期。

## 5. 跨仓变更顺序

先以具体用户场景形成契约提案，定义生产者与消费者的接受/拒绝例子。生产者发布可复现实现后，消费者使用精确版本接入，完整组合运行真实案例，最后更新集成锁与发布记录。

对同时开发的多个仓库，可以使用受控临时组合进行联调，但必须明确它不等于正式发布组合。临时 path/patch、工作目录和未提交变化应在正式验收前消除或纳入可复现来源。

新增与兼容调整优先；需要破坏性变更时，为旧工程与旧消费者提供明确兼容窗口或迁移。跨进程语义兼容测试与同进程 Rust 类型来源一致性分别检查。

## 6. 代表性架构门禁（建议实施）

| 门禁 | 目的 | 不能替代什么 |
|---|---|---|
| 依赖允许清单 | 禁止领域算法依赖 UI，禁止消费者直接依赖对方私有存储 | 不证明算法正确 |
| 公共 API/Schema 变更检查 | 捕获契约破坏及重复类型来源 | 不证明授权/业务语义 |
| 真实消费者契约测试 | 保证新 Producer 的实际消费路径可用 | 不证明整机运行链 |
| 工件闭包校验 | exact revision/hash/输入引用匹配 | 不证明几何精度与安全 |
| 业务黄金场景 | A/B、多 Setup、采纳冻结、NC 执行等真实链路 | 不覆盖未声明能力 |
| 负例与故障注入 | 验证未知语义、错帧、迟到结果、强杀、磁盘错误等处理 | 不自动证明所有异常已覆盖 |
| 发布组合验收 | 源码、二进制、原生库、资源包与被测版本一致 | 不替代生产现场批准 |

## 7. 团队协作试点

建议以“新增一种已定义刀路参数并形成 CL”与“新增一个只读知识检索/建议任务”作为两组并行试点。两组分别修改领域实现与自己的任务贡献，公共宿主只消费稳定协议。若仍需要同时修改大量 Shell 分支、公共数据库和对方内部模块，应把这些改动记录为边界缺口，而不是用临时直连解决。

试点不要求引入多人在线共同编辑、远程服务集群或动态不受信任插件。首先证明团队在独立环境中能开发、测试、集成和回退。
