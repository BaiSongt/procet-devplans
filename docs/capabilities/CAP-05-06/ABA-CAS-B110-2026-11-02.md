# B110｜CAP-05-06：ABA同Hash异修订、写点CAS与幂等对账研究（2026-11-02）

> V0.8原编号不变；L1/L2不改、L3待人类评审。此处是规划/合成证明，**不是D05/D08产品验收**，不触碰用户数据库、产品源码、付费CI或真实机床。

## 1. 问题和可证伪反例

D05发生 A(r14, hash=A, epoch=9) → B(r15, hash=B, epoch=10) → A(r16, hash=A, epoch=11)；旧Agent持有r14，按**单纯内容hash**比较会误把r16视为无变化。若据此写回，D08冻结、审计链和D06/D07/D09失效关系都可能错接。**内容相同≠同一不可变修订身份**。本项要求写点同时比较expected`id/scope/revision/contentHash/lineageEpoch`，并保留parentExactRef；此为Procet内生协议，不是RFC强制的CAD字段。反例中旧r14写请求必须为STALE，即使r16 hash=A。

HTTP RFC9110 §13.1.1的If-Match使用强比较避免representation丢失更新；**不能直接拿ETag代替领域revision**。SQLite官方§2.2明确BEGIN IMMEDIATE可提前申请写事务且可能SQLITE_BUSY；UPDATE WHERE不命中为零行，RETURNING可核对更新行。规划写侧应在同一SQLite事务执行`UPDATE ... WHERE exact_revision AND exact_hash AND lineage_epoch RETURNING...`，核对正好1行，追加新revision/审计/幂等回执后一起提交，否则回滚。该伪SQL只适用于单一受控数据库事务；跨库/Native/Worker并不天然享有分布式ACID。

**同域交互：** 左UnifiedTaskPanel“冻结→查看三方差异→提交预览→受管签署→结果/对账”，单Babylon Engine/Scene/Canvas只展示高亮，最大12px，浅/深主题。CLI与Agent复用相同Port；Agent没有直接写权限。成功/中断/重试可查询`requestId + exactReceipt`；取消后如发现已提交事实，只转`RECONCILE_ONLY`，禁止再提交或把晚回执渲染为新成功。真实撤销必须走新修订或补偿而不是删除历史。

## 3. 可复核证据层级及限制

- RFC 9110 (Fielding/Nottingham/Reschke，2022-06) §13.1.1/13.2，公开正文选段：仅给HTTP条件请求语义，不保证业务CAS。
- SQLite Project（页面无统一出版日） Transaction §2/2.2、UPDATE §2、RETURNING §1/3：合法公开正文选段；仅说明SQLite本地SQL行为，不证明产品使用的journal模式、跨库恢复或事务实现。
- W3C PROV-O (Lebo/Sahoo/McGuinness, 2013-04-30) §3 wasDerivedFrom/wasRevisionOf：来源表示方法，不是授权门禁。
- RFC 8785 (Rundgren/Jordan/Erdtman, 2020-06) §1/3：JCS内容稳定编码，不是唯一revision或ABA防护。没有宣称完整跨语言JCS实现。
- [CAP-05-06原业务规格](README.md)为仓库内生来源，ACL、D04/D10隔离、GUI布局不归因外部标准。
