## 4. 领域和协议设计

唯一Owner是**01域平台集成组合注册器**：持有`CombinationLock`的身份、不可变修订、激活状态与授权回执。各产品仓对自己的源码HEAD及构建产物来源各自负责。构建系统/离线实物是外部事实，01域仅登记可核证引用，不复制NC/几何/D01-D17业务主数据。C0只负责`DomainRef`、`ArtifactDescriptor`、`FrameRef`与协议版本，不创建巨大`common`。来源并不是批准、扫描到了manifest也不是后端ready。

核心设计对象：`CombinationLockId`、`researchSnapshotRefs[]`、`integrationManifestRef`、`dependencyClosure[]`、`targetPlatform`、`toolchainRef`、`nativeLibraryDescriptors[]`、`workerDescriptors[]`、`runtimeBundleDescriptor?`、`provenanceRefs[]`、`evaluationEvidenceRefs[]`、`compatibilityProfileRef`、`state`、`version`、`expectedRevision`、`requestId`。所有非可忽略引用采用**exact revision/hash**；`unknown`用缺失原因和后续责任表达，不能用全0哈希作默认值。`FrameRef`一般为`not_applicable`，不得把这个锁变成机床坐标权威。

业务状态分层：`draft`（只读采样）→`declared`（锁清单已发布草案）→`verified_inputs`（字节/版本/依赖闭包独立核对）→`tested`（目标平台/能力范围经真实执行）→`approved`（人工批准）→`active`（受控激活）。缺证据时保持`blocked/unknown`，而非升格；`retired`不删除历史。状态机、命令/查询/事件、`expectedRevision` CAS与幂等参见[接口文档](B0-01/01-combination-lock-contract.md)。业务成功回执必须区分Accepted、JobStarted、Validated、Committed，迟到回执也不可越过实际状态。

## 5. GUI / CLI / Agent 与同一领域事实

界面复用已存在Host、ModuleRegistry/ContributionHub/RendererPort及一个Babylon Scene；左侧UnifiedTaskPanel提供“观察→差异→闭包→验收→批准/激活”五个任务页，不另外新建3D实例。主工程与资源空间横向切换；选择某Consumer版本只生成只读Inspector/overlay并显示目标角色，不直接写`CombinationLock`。所有`copy path`/打开本机受控目录遵守授权，不把私有运行包推到公开仓。深浅主题一致展示状态颜色**和文字**；缺字节/来源显示`unknown`。

GUI、CLI和Agent必须调用统一的领域Query与Command；Agent建议不能自行批准；批准时角色/目标组合exact revision、证据闭包及策略版本重验。取消、后台任务晚回执和切文档必须持有`sessionId/epoch`，与Host Job生命周期统一。激活失败保留上一已批准组合，不改用户工程或数据库。与F1-04探索门禁、D04工艺Setup/D10机床绑定无隐性耦合。具体字段见[接口文档](B0-01/01-combination-lock-contract.md)。

## 7. 版本、失败和回退

锁升级采用`draft new revision`→`check compatibility`→`collect evidence`→`approve`→`CAS activate`。原锁以历史只读状态保存；可回退到已验证旧锁，但必须以**新激活事件**记录目标和原因，不能反向编辑历史声明。若Worker兼容性未能证明，限制为不启用该能力；缺Native/OCCT依赖须显式`blocked`。若HEAD漂移只更新新观察快照，不重写用户当前运行事实；文档评审失败则撤销待审计划，不回滚产品。
