**编制日：2026-10-19。原V0.8编号及L1/L2范围不变。** 当前状态：`规划草案已编制、待人类评审`。实现、独立clean-room验收、离线安装和用户批准均为 `NOT_RUN`。本草案只用于 `procet-devplans`；不修改产品仓、锁文件、开发者工作目录、用户数据或付费CI。**准确区分发布过程构建可再现、离线可构建、离线安装可运行三种目标。**

## 一、原始任务与经营风险

原V0.8《04_开发工作包_36项》写明：B0-04「消除发布对兄弟工作目录的依赖」，主责平台与集成、P0、01域；受影响 `procet-gui`、`procet-cam`；依赖 `B0-01`。原交付是“精确可复现的 CAM 消费入口、明确本地覆盖方式、双 workspace 构建入口”；验收是“干净检出组合无需未知本地修改，离线安装所需原生资产列齐，根 workspace 与 Tauri workspace 均在验收清单”；回退是恢复上次已经证明有效的组合锁与安装包；**不删除合法开发本地覆盖能力**。B0-02并非原V0.8的前置编号，但Owner目录和批准策略是本包跨域评审所需的并行治理输入，不能偷偷加成产品实现强依赖。

场景：开发者在 `procet-gui` 同级目录有 `procet-cam` 时，桌面端可以消费这个相对源；独立发布检出可能没有它；离线工厂安装不会携带开发者目录。**发布构建阶段必须显式供应并验证来源，安装运行阶段必须显式供应并验证必需Native/Worker**。发布资格不能由 manifest 存在、`cargo metadata` 成功、B0-01草案或成功展示GUI单独授予。支持两种合法发布策略：A）精确git revision并冻结Cargo.lock；B）授权的只读、按hash封存的源码供应包/受管vendor。选择哪一个属于L3评审，不宣称两种方案在所有环境等价或vendor天然有权再分发。

用户与角色：平台集成负责人（唯一B0-04交付Owner）、CAM领域维护者（CAM crate及ABI语义Owner）、桌面/前端构建负责人、Native/OCCT负责人、Worker负责人、独立质量验证者、离线交付审核者。真实生产者是各源码/依赖供应和打包流程；真实消费者是Host桌面运行、离线安装验证、B0-01运行锁、F1-01公共契约、F1-03领域接线和E3 NC纵向验证。**01域拥有受控发布组合记录，不拥有CAM业务数据或D01-D17领域真值。**

## 二、固定源码只读事实与不能越界的解释

2026-10-19只读GitHub `procet-gui@4e8eec12a212fc9dc86f2d728762c852832eebdb` 与 `procet-cam@fcec1c86047e6b11be35b8bb38971e3dfcffbd7b`：

| 准确位置 | 读到的事实 | 规划风险/证据缺口 |
|---|---|---|
| `apps/desktop/src-tauri/Cargo.toml` | `procet-cam = { path = "../../../../procet-cam" }`；本manifest末尾有独立 `[workspace]` | 在不提供兄弟目录的干净检出里**预期不能解析这个path**；本轮没有执行构建，不写成已复现FAIL |
| `integration-lock.json` | CAM源为`path+../procet-cam`，钉`fcec1c86…`并附声明`workspaceDigest`；solver钉`b7e8bfc5…` | 声明摘要尚未独立重算，且root锁不能替代Cargo实际解析闭包 |
| 根`Cargo.toml`与`Cargo.lock` | 根workspace含Host/Project/Bundle等成员且有锁文件 | 根workspace运行/验收**不涵盖**桌面独立workspace |
| 桌面`Cargo.lock` | Tauri使用另一份Cargo lock | 需要两个`--locked`结果和依赖图，不可汇报“一份Cargo PASS” |
| `pnpm-workspace.yaml`与`pnpm-lock.yaml` | `packages/*`,`apps/*`，版本9锁结构；desktop使用`workspace:*`内部链接 | frozen和offline需分别验证；锁存在≠本地store已备齐 |
| `apps/desktop/src-tauri/build.rs` | 环境变量`PROCET_OCCT_ROOT`存在时编译C++原生桥 | build.rs条件执行≠目标平台实际DLL可加载或ABI正确 |
| `tauri.conf.json` | 读到`bundle.active=true`、`targets=all`，此配置未列`externalBin/resources` | 不能推定全部Worker/Native不存在：其它代码/打包流程与安装实物尚未审计 |
| CAM自身`Cargo.toml` | `procet-contracts/resources/solver-adapter`有git精确rev | 正式切换CAM来源时必须验证传递依赖与feature；不默认升级Solver到研发HEAD |

重点区别：GUI根`Cargo.lock`、桌面`Cargo.lock`、pnpm锁是三份**不同层**的消费声明；Native运行动态库与Worker本身不是这些文件的充分产物。B0-01“研发HEAD、集成清单、运行实物”三层原则在本包被延续，且无实物时运行层标`UNKNOWN`。不能将“有两个Cargo.lock”推断成“已能离线构建”。

## 三、发布profile及业务流

**主流：** 选择已批准的B0-01三组合草案→按`sourceRef/revision/hash`解析CAM发行源→强制无兄弟目录的clean-room检出→分别核pnpm、根Cargo、桌面Cargo三锁→构建/读取Native与Worker供应清单→对目标系统生成**待验收**发布候选→独立质量组复算工件和installer字节→人类批准→01域CAS激活。`Approved`前所有阶段均不得称生产ready；任何真实命令和结果应在实施任务的独立测试入口中产生。

**替代流（研发覆盖）：** 研发用显式`dev_override`绑定本地CAM工作树，并记录路径、hash、dirty状态和工具链。它可产生“研发观察”但不可能直接升级“发布候选”。覆盖仅能经局部编译器配置启用，不修改已批准发布profile本身；发布模式必须拒绝path覆盖，不能因构建成功自动批准。

**异常流：** CAM仓不可用/路径缺失→`missing_source`；git撤回或hash失配→`source_mismatch`；双Cargo或pnpm锁变动→`lock_drift`；离线store缺包→`offline_cache_missing`；Native ABI不明→`native_unknown`；Worker未打包→`worker_missing`；安装包无真实hash→`runtime_unverified`；版本CAS冲突或权限失效→`commit_rejected`。每种阻断均保留上个已通过组合，不删除本地开发环境，不篡改历史快照。网络不可用时也应给出“缺哪份来源材料”的可行动作，不把缓存命中记录伪造成有效授权。

## 四、唯一Owner、合同字段与字段级约束

01域`ReleaseCombinationRegistry`（**拟议Owner，L3待审**）登记不可变发布组合及状态；CAM Owner拥有CAM crate API/ABI契约，Native Owner拥有OCCT运行文件来源，桌面Owner拥有Tauri构建描述符，Worker Owner拥有sidecar协议。C0仅传`ArtifactRef`、`RevisionRef`、`UnitRef`、`FrameRef`、`ProtocolVersion`，不搬运领域对象。标准坐标并非本包约束：`frameRef=not_applicable`应显式保存，不能捏造机床坐标。

关键字段及来源：`combinationLockRef`/`expectedRevision`来自B0-01；`camSource.kind`枚举`git_exact|signed_source_archive|dev_override`（`dev_override`不得进入发布）；`camSource.commit`为40位Git SHA（*如果git方式*）；`manifestDigest`、`workspaceDigestMeasured`、`rootCargoLockDigest`、`tauriCargoLockDigest`、`pnpmLockDigest`为字节摘要（统一`sha256:`前缀，验收前不得填默认hash）；`targetTriple`为目标平台明确文本、不是由B5机床名派生；`toolchainRef`及`occtSdkAbi`来自Native配置；`nativeArtifacts[]`与`workerArtifacts[]`含相对包内位置、目标平台、expected SHA、实际measured SHA、license/provenance、签名/许可状态（未知显式unknown）；`buildEvidenceRef`、`offlineInstallEvidenceRef`、`publishedBundleRef`是不同证据；`approvalRef`由人类签署；`requestId`、`editSessionId`、`routeEpoch`解决幂等/晚到事件；`publicationStatus`从`draft|declared|source_verified|build_tested|install_tested|approved|active|blocked|retired`取值。后四者要明确目标平台与能力覆盖；**没有实测字节时不得越级。**

每个业务事件需含`assetId/exactRevision/contentHash/protocolVersion/requestId/actor/previousRevision/observedAt/committedAt`。只有`Committed`回执会改变领域真值，`Accepted`/`JobStarted`/`Validated`不会。CAS冲突、异步已取消或旧`routeEpoch`回执必须幂等拒绝且提供无业务写入的重试/查询动作。任何审批要在提交点重新验证目标exact版本、策略版本与证据闭包。见[接口与GUI](B0-04/01-dependency-contract-and-gui.md)。

## 七、迁移、版本和回退原则

**expand**：只新增受管来源profile与可观测状态，不阻断现有开发path覆盖；**migrate**：开发者在明确`dev_override`下继续迭代，发布流水线使用`git_exact`或获得授权的自包含来源闭包；**contract**：只有在真实消费方逐一迁移并通过清洁构建/安装回归后，才能停用发布环境旧隐式path读取。不能在本工作包直接修改产品或删路径。程序/资源运行数据不迁移，不删除用户目录。失败时发布登记记录append-only标阻断，恢复上次`approved+measured`组合及其匹配installer/Native/Worker，激活通过新事件完成，历史不覆盖。版本升级要先验证三锁、目标编译器、平台ABI、Worker协议及消费者测试，缺一即fail-closed。

## 八、设计冻结边界与开放问题

L1/L2沿用V0.8，L3的CAM发行方式、证据协议、离线供应权限、签名策略以及`ReleaseCombinationRegistry`Owner需要用户/集成负责人评审；L4不做最终冻结。开放问题：团队是否批准源码vendoring/二次分发？正式交付目标是否只有Windows x64 MSVC？Native/Worker真实工件由谁生产、存于何处？2D/Docs/Agent及后续模块何时纳入同一发布列车？这些均不能凭旧`integration-lock.json`臆断。**先拿到真实安装包与可复现构建结果，再声称发布工程验收。**
