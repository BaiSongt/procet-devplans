## 业务目标与责任域
数控后处理生成的D12 NC原文必须由独立的D13适配处理，而不能拿D09中立CL画面冒充机床运动或D15工程验证。数据顺序：**D09 CL → D12 NC后处理 → D13控制器语义 → D14轴时序 → D15程序级工程验证 → D16批准发布**。D11仅CL级预验证。未知宏、循环、专有G/M、未锁定偏置或刀表返回 UNKNOWN，不得吞错通过。

D12由08域NC生成负责原文字节、programHash和源码段；D13由08域执行适配持有规范化事件，不重写D12；D10由04域执行配置持有，引用02域资源，与D04工艺Setup分离；D14/D15由09域独立计算和验收，D16由10域发布Owner批准。D08冻结快照与A/B共同事实不可原地覆盖，C0只提供通用身份/哈希/Frame/CAS等最小约束。

## 正常业务流程与状态
1. 用户从NC工序树选择精确D12 revision+SHA256，明确D10 binding revision、机床/控制器profile exactHash、刀表/偏置/Frame与单位。输入不足先呈现 UNKNOWN，不用最新可用配置猜测。
2. GUI/CLI/Agent通过同一个 **NcExecutionPort.interpret** 调用；Host生成taskId，超时、取消和审计事件统一编排。开始计算前读取授权、冻结范围和精确输入。
3. 解析D12原始NC的语法块、模态组、G90/G91、G20/G21、G54等偏置、刀补及M码。每个已覆盖事件携带sourceSpan、原始blockHash、前后modalHash、D10引用；unsupportedFeatures显式记录。
4. 仅全部已声明范围闭合时产生 READY_FOR_D14；未知语义为 UNKNOWN，违规/冲突为 REJECTED；不产生D14轴轨迹，也不发D15/D16通过结论。
5. 尝试写入D13新不可变候选时，再校验权限、currentRevision==expectedRevision、Frame和任务取消状态；晚回执被拒绝采纳但可保留只读审计。D14独立消费方据此验证其输入闭包。
