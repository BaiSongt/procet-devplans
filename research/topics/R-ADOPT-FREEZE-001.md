# R-ADOPT-FREEZE-001｜候选采纳与局部冻结的证据边界
[W2-02原工作包](../../docs/work-packages/W2-02.md) · [8条来源登记](../sources/W2-02.json) · [10规则及20正反](../traces/W2-02.json)

**研究问题**：当D06同时输出多条带几何证据的候选工序，如何将特定候选映射至05域D05/D08而不覆盖用户冻结的工程决定？同时需在多分支、重排、取消与并发更新中保留稳定来源。

1. ISO 14649-10:2004官方公开摘要确有workingsteps/workplan控制结构，但**不规定**具体冻结、回退算法；Procet采用StableStepUID避免index误绑是内部设计决策。标准正文未读。
2. W3C PROV-O可表达候选来源、修订和采纳活动；并不提供CAS或领域批准。RFC 9110§13.1.1的If-Match强比较只能作为防丢更新思路；独立05域写入仍需事务、ACL、任务代次。
3. RFC 8785涉及JSON规范化的适用前提，不能把未选定的canonicalizer或原NC字节哈希视为已实现。Git三方合并说明显式冲突的交互逻辑，但B-Rep同一空间不同工序的语义冲突必须由几何/工艺规则决定，不使用文本行合并判断。
4. OCCT BRepCheck_Analyzer的IsValid只检查形状有效性；D07需要独立材料状态和布尔结果证据，SEARCH_FEASIBLE仍不能授D09/D15资格。Google CP-SAT的UNKNOWN只是其整数求解器求解状态；不外推为OCCT产品求解正确。NIST仅出版摘要用于跨域数字线程背景，不作接口合规声明。

**可证伪规则**：W202-R01~R10对稳定身份、exact引用、D07证据、冻结、分支、三方差异、幂等、CAS/权限、取消回执、下游资格逐项映射字段并配正反例。实际执行检查须比对冻结前后真实字节hash、用独立05域持久消费者运行；本轮仅规划语义合成。
